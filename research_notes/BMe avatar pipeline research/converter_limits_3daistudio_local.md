# Image-to-3D converter input limits, preprocessing and local feasibility: 3D AI Studio vs local Hunyuan3D 2.x / TRELLIS / TRELLIS.2 / part-aware generators (as of 2026-10-10)

Research date: 2026-10-10. Target hardware for the "local" questions: Windows PC, RTX 5070 Ti (16 GB, Blackwell sm_120), 64 GB RAM, ComfyUI.

Evidence labels used throughout: **Documented** (official repo/README/code/docs), **Observed** (community demonstration, issue thread, third-party test), **Inferred** (my derivation from documented constants), **Unverified** (claim found only in secondary/SEO sources or not reachable). Nothing in this file was tested by me.

Access note: the sandbox proxy returned HTTP 403 for `3daistudio.com`, `docs.3daistudio.com`, `docs.comfy.org`, `blog.comfy.org`, `arxiv.org`, `huggingface.co`, `hf-mirror.com`, `ar5iv.labs.arxiv.org` and `comfyui-wiki.com`. ## Key Question 1: 3D AI Studio (3daistudio.com) — which models it wraps, input limits, credits, web vs API, preprocessing

### Takeaway
3D AI Studio is a multi-vendor aggregator: as of mid/late 2026 it exposes Tencent Hunyuan 3D 3.0/3.1 (Pro and Rapid editions, API-only models from Tencent), Microsoft TRELLIS.2-4B, TencentARC Pixal3D, Tripo (branded "Prism"), Deemos/Hyper3D (branded "Forge"), Hitem3D (Sparc3D), Meshy and others. Public docs give only soft input guidance (PNG/JPG/JPEG[/WebP], ≤50 MB per file, "at least 1024×1024 recommended"); no maximum pixel dimension, aspect-ratio rule, or server-side resize/crop behaviour is publicly documented ("not publicly verified").

### Inferences
- Because the platform's Hunyuan is Tencent's hosted 3.0/3.1 (not the open 2.x weights), **nothing in the open Hunyuan3D-2.x code tells you what resolution 3D AI Studio's Hunyuan actually conditions on**; the 2.x preprocessing facts below are only a lower-bound analogy (Inferred).
- "Recommended 1024×1024" plus a 50 MB cap and no documented maximum dimension suggests the service resizes internally, but **that is not publicly verified**. Tripo's `enable_image_autofix` flag shows at least one vendor path does server-side image "fixing" when enabled.
- Web app vs API: pages found describe the same models and credit costs for both; no evidence of different pixel limits by plan or surface (Unverified either way).

### Gaps
- Max input width/height, total-pixel cap, aspect limits, and whether input is resized/cropped before reconstruction: **not publicly verified**. Pages checked (via snippets only, proxy-blocked for direct read): `/Models`, `/Models/Trellis-2`, `/Models/Hunyuan3D-3-1`, `/Models/Pixal3D`, `/Models/Hitem3D`, `/ModelComparison`, `/Pricing` (not retrievable), `/Platform`, `/Platform/API/Trellis2`, `/Platform/API/Hunyuan3D`, `/Platform/API/Documentation/3d-generation`, `/Platform/API/Documentation/3d-generation/tencent-hunyuan`, `/Platform/API/Documentation/3d-generation/tripo`, `docs.3daistudio.com/troubleshooting`, `/faq`, `/workflow-examples`, `/3d-generation/text-to-3d`, `/textures/texture-generator`, `/Updates`.
- Whether the base64 payload has a size cap in the API: not found.
- Exact Hunyuan checkpoint behind "Pro"/"Rapid" (Tencent's naming): not published.

## Key Question 2: Hunyuan3D 2.x (2.0, 2mini, 2mv, 2.1) — exact conditioning preprocessing, effective input resolution, texture pipeline resolutions, VRAM, ComfyUI status, Blackwell/Windows

### Takeaway
Hunyuan3D-2.x shape models see a **518×518** DINOv2 input (2.0 paper: DINOv2-Giant; 2.1 training config: `facebook/dinov2-large`, `image_size: 518`), produced from a 512×512 recentered/white-padded image where the object's long side is scaled to 512×(1−0.15)=435 px. The texture pipelines generate multi-view images at **512×512** (2.0: 6 views, 2.1: up to 6 selected views) and bake to **2048** (2.0) or **4096** (2.1, after RealESRGAN ×4) textures. Shape gen fits in 6–10 GB; texture gen for 2.1 is ~21 GB officially and is the part that does not fit 16 GB without community low-VRAM builds. ComfyUI native nodes do shape only; texturing requires kijai's wrapper or visualbruno's 2.1 nodes, which need a compiled `custom_rasterizer` — the single biggest Blackwell/Windows failure point in 2026 issue threads.

### Cited Findings

**Model zoo and dates (Documented):**
- Hunyuan3D-DiT-v2-0 (1.1B, 2025-01-21), -Fast (2025-02-03), -Turbo (2025-03-19); Hunyuan3D-Paint-v2-0 (1.3B, 2025-01-21), Paint-v2-0-Turbo (2025-04-01), Delight-v2-0 (1.3B); Hunyuan3D-DiT-v2-mini / -Fast / -Turbo (0.6B, 2025-03-18/19); Hunyuan3D-DiT-v2-mv / -Fast / -Turbo (1.1B, 2025-03-18/19); 2.1 series DiT-v2-1 (3.0B) and Paint-v2-1 (1.3B) dated 2025-06-13 — [Hunyuan3D-2 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/README.md). The 2.1 repo lists Hunyuan3D-Shape-v2-1 as 3.3B and Paint-v2-1 as 2B (2025-06-14) — [Hunyuan3D-2.1 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/README.md). (Parameter counts differ between the two READMEs; both are Tencent's.)

**Shape conditioning preprocessing — official code (Documented, read from source 2026-10-10):**
- `hy3dgen/shapegen/preprocessors.py` (Hunyuan3D-2, `main`): `ImageProcessorV2(size=512, border_ratio=None)`; `recenter()` crops to the bounding box of the non-zero mask, scales so the longer side = `int(size*(1-border_ratio))`, centres on a square canvas, composites on **white**; `load_image(border_ratio=0.15)` recenters then resizes to `size×size` with `cv2.INTER_CUBIC` (mask `INTER_NEAREST`); `array_to_tensor` maps to [-1,1]. If there is **no alpha channel the mask is set to all-255 (whole image = foreground)** — i.e., this class does **not** remove backgrounds. `MVImageProcessorV2` maps views `front=0, left=1, back=2, right=3` and stacks them — [preprocessors.py (2.0)](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/preprocessors.py). The 2.1 copy is functionally identical (size 512, border 0.15, white bg, INTER_AREA for recenter resize, INTER_CUBIC final) — [preprocessors.py (2.1)](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/hy3dshape/hy3dshape/preprocessors.py).
- `hy3dgen/shapegen/models/conditioner.py`: `DinoImageEncoder` transform = `Resize(image_size, BILINEAR, antialias=True)` → `CenterCrop(image_size)` → Normalize ImageNet mean/std; `num_patches = (image_size//14)**2 (+1 CLS)`; class default `image_size=224` but the actual value is set from the model config. `DinoImageEncoderMV` adds a 1D sin-cos view embedding per view (`view_num=4`) and flattens `num_views × tokens` — [conditioner.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/models/conditioner.py).
- **518 confirmed in 2.1 training config:** `hunyuandit-finetuning-flowmatching-dinol518-bf16-lr1e5-4096.yaml` → `cond_stage_config: type: DinoImageEncoder, version: 'facebook/dinov2-large', image_size: 518, use_cls_token: true`; `image_processor_cfg: target: hy3dshape.preprocessors.ImageProcessorV2, params: {}` (so size 512 default); dataset `image_size: 518`; header "VAE: 4096 token length" — [config yaml](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/hy3dshape/configs/hunyuandit-finetuning-flowmatching-dinol518-bf16-lr1e5-4096.yaml); [configs dir](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/tree/main/hy3dshape/configs).
- **518 / DINOv2-Giant in the 2.0 paper (Documented, snippet of arXiv HTML):** "we utilize a large image encoder – DINOv2 Gaint and large input image size – 518×518" — [arXiv 2501.12202 HTML](https://arxiv.org/html/2501.12202v1). A later Tencent paper restates: "first resized to 518 × 518, removed background and then encoded by a frozen DINOv2 backbone" — [Hunyuan3D Studio paper, arXiv 2509.12815](https://arxiv.org/html/2509.12815v1).
- Pipeline defaults (`hy3dgen/shapegen/pipelines.py`): `octree_resolution=384`, `num_chunks=8000`, `mc_level=0.0` (flow-matching pipeline), `num_inference_steps=50`, `guidance_scale=5.0`, `box_v=1.01`; no rembg inside the pipeline — [pipelines.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/pipelines.py).

**Texture pipeline resolutions (Documented, read from source):**
- 2.0 `hy3dgen/texgen/pipelines.py`: `self.render_size = 2048`, `self.texture_size = 2048`, 6 candidate cameras azimuths `[0,90,180,270,0,180]`, elevations `[0,0,0,0,90,-90]`, weights `[1,0.1,0.5,0.1,0.05,0.05]`, `bake_exp = 4`, `recenter_image(border_ratio=0.2)`, delight model applied once per reference image, multiview outputs resized to `render_size` before baking, `uv_inpaint` fills holes; default subfolder `hunyuan3d-paint-v2-0-turbo` — [texgen/pipelines.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/texgen/pipelines.py).
- 2.0 `hy3dgen/texgen/utils/multiview_utils.py`: `view_size = 512`; width/height 512; `num_inference_steps=30`; reference and control images resized to 512×512 **without aspect preservation**; fp16 — [multiview_utils.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/texgen/utils/multiview_utils.py). DeepWiki (third party) also notes MeshRender at 2048×2048 — [DeepWiki Hunyuan3D-Paint](https://deepwiki.com/Tencent/Hunyuan3D-2/4.2-texture-generation-(hunyuan3d-paint)).
- 2.1 `hy3dpaint/textureGenPipeline.py`: `Hunyuan3DPaintConfig(max_num_view, resolution)` with `render_size = 1024*2` (2048), `texture_size = 1024*4` (4096), `dino_ckpt_path = "facebook/dinov2-giant"`, `realesrgan_ckpt_path = "ckpt/RealESRGAN_x4plus.pth"`, `bake_mode = "back_sample"`, `bake_exp = 4`, six primary cameras plus 24 low-weight ring cameras at ±20° elevation; reference image resized to **512×512** and RGBA composited on white; multi-view PBR (albedo + metallic-roughness) generated at `config.resolution`, passed through RealESRGAN ×4, resized to `render_size`, baked, inpainted; README example uses `max_num_view=6, resolution=512` — [textureGenPipeline.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/hy3dpaint/textureGenPipeline.py); [Hunyuan3D-2.1 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/README.md).

**VRAM (Documented unless noted):**

- 2.1: shape ≈10 GB, texture ≈21 GB, both ≈29 GB; `--low_vram_mode` — [Hunyuan3D-2.1 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/README.md). - ComfyUI docs (snippet): mini "requires only 5GB VRAM", standard "6GB VRAM for shape", full shape+texture "12GB" — [docs.comfy.org Hunyuan3D-2 tutorial](https://docs.comfy.org/tutorials/3d/hunyuan3D-2).

**ComfyUI native nodes (Documented, source read 2026-10-10):**
- `comfy_extras/nodes_hunyuan3d.py`: `EmptyLatentHunyuan3Dv2` (resolution default 3072 tokens), `Hunyuan3Dv2Conditioning` (takes `CLIP_VISION_OUTPUT.last_hidden_state`, negative = zeros), `Hunyuan3Dv2ConditioningMultiView` (front/left/back/right, sinusoidal view embedding over 4 views, concatenated), `VAEDecodeHunyuan3D` (`num_chunks` default 8000, `octree_resolution` default **256**, min 16, max **512**), `VoxelToMesh` (`surface net` or `basic`, threshold 0.6). **No image resizing/cropping in this file.** — [nodes_hunyuan3d.py](https://github.com/comfyanonymous/ComfyUI/blob/master/comfy_extras/nodes_hunyuan3d.py).

### Inferences
- **Effective geometry conditioning resolution (Inferred from constants above):** object long side → 435 px inside a 512 canvas → bilinear resize to 518 → the object spans ≈ 440 px of a 518×518 DINOv2 input (37×37 = 1369 patch tokens + CLS). Any source detail finer than ~1/440 of the object's long dimension is discarded before the DiT sees it. A 4K–8K master image offers **no additional geometric information** to Hunyuan3D-2.x beyond acting as a cleaner downsample source.
- **Effective texture conditioning resolution (Inferred):** reference image → 512×512 (2.0 and 2.1); generated views 512² (upsampled ×4 by RealESRGAN in 2.1 to 2048 render, baked to 4096 UV). The 4K texture in 2.1 is therefore **super-resolved synthesis**, not transfer of 4K source pixels. Larger inputs help only marginally via better downsampling.
- **Geometric resolution** is governed by the ShapeVAE decode `octree_resolution` (official default 384; ComfyUI native default 256, capped 512; kijai up to 4096 nominal) and marching cubes — independent of input image size.
- For a 16 GB RTX 5070 Ti: shape gen for 2.0/2mv/2mini/2.1 is well within budget (6–10 GB official). 2.0 texturing (16 GB total official; 6 GB with mmgp) is feasible; 2.1 texturing (21 GB official) is **not** feasible with stock code and would need WinPortable's mmgp path or reduced `view_size/texture_size` (community-reported, not official).
- Blackwell status (Inferred from issue threads): shape generation works with a cu128/cu130 torch build; **texturing is gated by compiling `custom_rasterizer` for sm_120 on Windows**, for which no official or kijai-prebuilt wheel exists as of 2026-07 (#214), with two community wheel PRs unmerged. The WinPortable CUDA 12.9 bundle is the only packaged route that explicitly lists Blackwell.

## Key Question 3: TRELLIS and TRELLIS.2 — preprocessing resolution, VRAM, Windows/Blackwell, ComfyUI, quality vs Hunyuan3D

### Takeaway
TRELLIS (Dec 2024) crops the object (1.2× bbox), resizes to **518×518**, multiplies RGB by alpha (black background) and encodes with DINOv2 at 518; README demands 16 GB VRAM and Linux. TRELLIS.2 (Dec 2025, 4B, MIT) downsizes to ≤1024 px long side, crops to the alpha bbox, and conditions at **512 and 1024** (DINOv3-L in ComfyUI's packaging); README demands **24 GB** and Linux, but ComfyUI made it a core node in v0.34.0 (26 Aug 2026) with int8 weights and memory reductions in v0.35.0; community 16 GB reports say the 32³ structure grid works and the 64³/1536 path pages to system RAM or OOMs. Independent character-specific head-to-heads versus Hunyuan3D were not found; vendor comparisons conflict.

**TRELLIS (microsoft/TRELLIS) (Documented):**
- Models: TRELLIS-image-large 1.2B (image-conditioned recommended); "An NVIDIA GPU with at least 16GB of memory is necessary"; "The code is currently tested only on Linux"; Windows via issue #3 ("not fully tested"); CUDA 11.8/12.2 tested, default env torch 2.4.0+cu118; deps flash-attn (default backend), xformers alternative, spconv, kaolin, nvdiffrast, diffoctreerast, mip-splatting; `to_glb(..., simplify=0.95, texture_size=1024)` in the example; 2024-12-18 multi-image conditioning added — [TRELLIS README](https://github.com/microsoft/TRELLIS/blob/main/README.md).

## Key Question 4: 2026 part-aware / component-output generators relevant to a modular robot avatar

### Takeaway
Open options that output separate parts fall into two classes: **image → multi-part meshes directly** (PartCrafter, MIT, ≥8 GB; PartPacker, NVIDIA non-commercial, ~10 GB) and **mesh → segmented/completed parts** (Hunyuan3D-Part P3-SAM + X-Part, Tencent community license, light release; HoloPart). None include texturing; all are geometry-only, so a modular robot workflow would be: generate parts → texture per part with a separate pipeline.

### Cited Findings
- **PartCrafter** (wgsxm/PartCrafter; NeurIPS 2025): "jointly synthesizes multiple semantically meaningful and geometrically distinct 3D meshes from a single RGB image" without a separate segmentation step; arXiv 2025-06-09, code fully open-sourced 2025-07-13; base model TripoSG (DiT finetuned, VAE fixed); inputs single RGB image + `--num_parts` (or VLM `--part_suggest`); `--rmbg` uses RMBG-1.4 and resizes (target res not stated); "A CUDA-enabled GPU with at least 8GB VRAM"; tokens 1024 per part (objects) / 2048 (scenes); training configs mp8/mp16 imply up to 16 parts; **MIT**; texture not mentioned; Windows via community fork/PR #24 — [PartCrafter README](https://github.com/wgsxm/PartCrafter); [arXiv 2506.05573](https://arxiv.org/abs/2506.05573v1). Third-party: Chamfer 0.1726 vs HoloPart 0.1916 on Objaverse; 34 s vs 18 min — [3D Printing Industry](https://3dprintingindustry.com/news/partcrafter-open-source-ai-tool-converts-2d-image-into-geometrically-distinct-3d-meshes-240627/).
- **PartPacker** (NVlabs/PartPacker, arXiv 2506.09980): "part-level 3D object generation from single-view images" via dual volume packing; "~10GB GPU memory (assuming float16)"; Windows section tested on 3090/4090; multi-GPU mode; license = **NVIDIA Source Code License: "only may be used or intended for use non-commercially"** — [PartPacker README](https://github.com/NVlabs/PartPacker); [license.md](https://github.com/NVlabs/PartPacker/blob/main/license.md).
- **HoloPart** (VAST-AI-Research/HoloPart, arXiv 2504.07943, Apr 2025): two-stage — existing segmenter (e.g., SAMPart3D) produces visible patches, diffusion model completes each into full parts incl. occluded geometry; input is a **3D mesh**, not an image — [arXiv 2504.07943](https://arxiv.org/abs/2504.07943v1); [HF paper page](https://huggingface.co/papers/2504.07943).
- **Hunyuan3D-Part** (Tencent-Hunyuan/Hunyuan3D-Part; papers arXiv 2509.06784 P3-SAM, 2509.08643 X-Part, Sep 2025): "The holistic mesh is fed to part detection module P3-SAM" → semantic features, part segmentations, bounding boxes → X-Part "generates the complete parts"; input is a **mesh** ("can handle any input mesh"; for X-Part "scanned or AI-generated meshes (e.g., from Hunyuan3D V2.5 or V3.0)"); "The current release is a light version of X-Part", full version on Hunyuan3D-Studio; XPart README: Python 3.10, torch 2.4.0+cu121, Sonata dependency, pretrained-model download step marked **TODO** at time of reading (while HF `tencent/Hunyuan3D-Part` lists weights — status inconsistent); no VRAM stated; license "Tencent Hunyuan 3D-Part Community License" (2025-09-23): not applicable in EU/UK/South Korea, 1M MAU threshold — [Hunyuan3D-Part README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Part); [XPart README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Part/blob/main/XPart/README.md); [LICENSE](https://github.com/Tencent-Hunyuan/Hunyuan3D-Part/blob/main/LICENSE); [HF repo](https://huggingface.co/tencent/Hunyuan3D-Part/blob/main/README.md).
- **Hunyuan3D-Omni** (2025-09-25, arXiv 2509.21245): controllable shape generation inheriting Hunyuan3D 2.1 (~3.3B); controls = bounding box, **pose/skeleton ("Create 3D human models with specific skeletal poses")**, point cloud, voxel; "It takes 10 GB VRAM for generation"; Python 3.10 / torch 2.5.1 / CUDA 12.4; shape only (no texture/rigging); "Tencent Hunyuan 3D Omni Community License" (2025-09-26), EU/UK/KR excluded, 1M MAU — [Hunyuan3D-Omni README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Omni); [License.txt](https://github.com/Tencent-Hunyuan/Hunyuan3D-Omni/blob/main/License.txt).
- Vendor "parts" features on 3D AI Studio: none found in the pages/snippets reviewed (Gap).

### Inferences
- For a modular robot avatar on a 16 GB GPU, the only direct image→parts options are PartCrafter (commercial-OK, 8 GB) and PartPacker (non-commercial). Neither produces textures, so per-part texturing must be done with Hunyuan3D-Paint (2.0 fits 16 GB; 2.1 does not) or TRELLIS.2 texture stage (shape-conditioned texture generation is listed as released in its roadmap).
- Hunyuan3D-Part's mesh-in/parts-out design means it can post-process any whole-body mesh (e.g., from TRELLIS.2 or Hunyuan3D-2.1), subject to the light-release limitation and the license territory.

### Gaps
- VRAM for P3-SAM/X-Part and HoloPart: not stated anywhere found.
- No ComfyUI nodes found for PartCrafter, PartPacker, HoloPart or Hunyuan3D-Part.

## Key Question 5: Other 2026 candidates for character/figure reconstruction (Hi3DGen, Step1X-3D, Direct3D-S2, Sparc3D/Hitem3D, Pixal3D, Hunyuan3D 3.x)

### Takeaway
Pixal3D (TencentARC, SIGGRAPH 2026, MIT, TRELLIS.2 backbone, native in ComfyUI since v0.34.0, multi-view since Sep 2026) is the most relevant open 2026 model; Direct3D-S2 (MIT, 10 GB @512³, 24 GB @1024³, geometry only) and Hi3DGen (MIT, TRELLIS-derived, geometry only) are feasible geometry-only options; Step1X-3D needs 27–29 GB; Sparc3D has no public code/weights (commercial via Hitem3D); Hunyuan3D 3.0/3.1/3.5 are cloud-only.

### Cited Findings
- **Pixal3D** (TencentARC/Pixal3D, arXiv 2605.10922): SIGGRAPH 2026 (Apr 2026); inference code + demo May 2026; TRELLIS.2-based `main` branch, Direct3D-S2-based `paper` branch; training code May 2026; **multi-view inference Sep 2026**; MIT (third-party components keep their licenses); inference default **1536** standard / **1024** low-VRAM ("loads models on-demand"); single-image path does background removal; multi-view images "are never cropped or rescaled, so framing must match the camera parameters", first view = canonical front; `natten` must be built for your CUDA arch; `ATTN_BACKEND=sdpa` without flash_attn; community Pixal3D-ComfyUI with Windows/WSL guides — [Pixal3D README](https://github.com/TencentARC/Pixal3D). License conflict: one outlet says MIT, another "academic-only" — [startupfortune MIT](https://startupfortune.com/pixal3d-goes-mit-open-source-for-3d-asset-creation/); [startupfortune academic](https://startupfortune.com/pixal3d-makes-image-to-3d-feel-closer-to-a-working-pipeline/). ComfyUI native (v0.34.0): `Pixal3DConditioning` camera FOV default 49.13°, `pad_factor=1.1`, multi-view node upsamples views to 1024×1024 — [nodes_trellis2.py](https://github.com/comfyanonymous/ComfyUI/blob/master/comfy_extras/nodes_trellis2.py); docs tutorial lists MoGe in `models/geometry_estimation` — [Pixal3D tutorial (snippet)](https://docs.comfy.org/tutorials/3d/pixal3d).
- **Hi3DGen** (Stable-X/Hi3DGen, arXiv 2503.22236): "adapted from TRELLIS", MIT, NVIDIA kaolin/nvdiffrast/flexicube dependencies removed "so the adapted version can be used commercially"; VRAM, input resolution, Windows, ComfyUI and texture support not stated — [Hi3DGen README](https://github.com/Stable-X/Hi3DGen). Secondary: normal-bridging, compared against CraftsMan-1.5, Hunyuan3D-2.0, Clay, Tripo-2.5, Trellis, Dora — [ComfyUI-wiki news (secondary)](https://comfyui-wiki.com/zh/news/2025-04-07-hi3dgen-stable-x).
- **Step1X-3D** (stepfun-ai, 2025-05-13): Geometry 1.3B, Texture 3.5B; "Geometry-1300m with Texture uses 27G GPU memory", Label variant 29G, 152 s/50 steps; Apache-2.0; ComfyUI unchecked in roadmap; multi-view/bbox/skeleton conditioning planned, unchecked — [Step1X-3D README](https://github.com/stepfun-ai/Step1X-3D).
- **Direct3D-S2** (DreamTechAI, NeurIPS 2025, arXiv 2505.17412): v1.0/v1.1 released 2025-05-30; "v1.2 with better character generation" in preparation as of 2025-06-03; `sdf_resolution` 512 or 1024 (512 discouraged); inference ≥10 GB @512, ~24 GB @1024; MIT; `.obj` geometry only; Windows via issues #11/#12; no ComfyUI — [Direct3D-S2 README](https://github.com/DreamTechAI/Direct3D-S2).
- **Sparc3D** (lizhihao6/Sparc3D, arXiv 2505.14521): README has abstract/citation/HF demo only; no code, weights, license or release instructions — [Sparc3D repo](https://github.com/lizhihao6/Sparc3D). Commercialised as Hitem3D / Hi3D ("proprietary models Sparc3D and Ultra3D"; Hi3D 2.1 launched 2026-05-14) — [Product Hunt Hitem3D](https://www.producthunt.com/products/hitem3d-2-0/launches/hitem3d).
- **Hunyuan3D 3.x**: see KQ1 — cloud/API only, 1536³, no open weights found.

### Inferences
- On 16 GB: Pixal3D low-VRAM (1024) via ComfyUI native is plausible (same memory profile as TRELLIS.2 native, Inferred); Direct3D-S2 only at 512³ (10 GB) which the authors discourage; Step1X-3D is out of budget without offloading; Hi3DGen's VRAM is unknown but, being TRELLIS-derived, likely ~16 GB class (Inferred).
- Pixal3D's multi-view path (no crop/rescale, camera-parameter-matched views) is the only open pipeline found where framing/resolution of each view is preserved into the model — making it the natural consumer of a carefully produced multi-view set rather than one stitched master.

### Gaps
- Pixal3D VRAM numbers (README gives none), its texture size, and its internal view resolution are undocumented.
- Hi3DGen quantitative/user-study numbers vs Hunyuan3D-2 could not be read (arXiv blocked).

## Key Question 6: Effective resolution summary — input vs geometry vs texture — and whether a 4K–8K source helps

### Takeaway
Every open converter examined downsamples the conditioning image to between 518² (Hunyuan3D-2.x, TRELLIS) and 1024² (TRELLIS.2 high-res branch, Pixal3D) before any geometry is generated, and texture references are reduced to 512² (Hunyuan3D-Paint) or ≤1024 (TRELLIS.2). A 4K–8K stitched master therefore cannot transfer extra detail to geometry or texture in these models; its only value is as a clean source for downsampled crops or per-view renders.

### Cited Findings (consolidated table; sources are those cited in KQ2–5)

| Converter / version | Input limit (documented) | Internal geometry-conditioning res | Texture-conditioning res | Output texture res | Geometric resolution control |
|---|---|---|---|---|---|
| Hunyuan3D-2.0 / 2mini / 2mv (open, Jan–Mar 2025) | none in code; alpha expected | 512² recenter (object ≤435 px) → 518² DINOv2-G ([preprocessors.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/preprocessors.py), [paper](https://arxiv.org/html/2501.12202v1)) | ref image → 512² ([multiview_utils.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/texgen/utils/multiview_utils.py)) | 6 views @512² → bake 2048² ([texgen/pipelines.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/texgen/pipelines.py)) | `octree_resolution` 384 default ([pipelines.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/pipelines.py)); ComfyUI native 256 default/512 max |

### Inferences
- For Hunyuan3D-2.x and TRELLIS the useful input ceiling is ≈ 600–700 px on the object's long side (anything more is discarded by the 512/518 resize after padding); for TRELLIS.2/Pixal3D ≈ 1024 px. Producing a 4K–8K master is justified only if it is the *source* from which (a) a tight 1024-px object crop and (b) per-view ortho renders/crops are derived.
- Texture detail in all local models is **synthesised** by multi-view diffusion at 512² and upscaled (2.1: RealESRGAN ×4) — a high-res master cannot be "projected" through these pipelines; to use the master's texture detail you would bake/project it yourself onto the generated mesh outside the generator.

### Gaps
- No vendor-published statement from 3D AI Studio or Tencent about the internal conditioning resolution of Hunyuan 3.0/3.1/3.5.

## Key Question 7: Does multi-view input preserve detail better than a single large image?

### Takeaway
Architecturally yes for the open models: each extra view in Hunyuan3D-2mv is a full 518² DINOv2 pass (4 views ≈ 4× the token budget, with sinusoidal view embeddings), and Pixal3D's multi-view path keeps view framing intact; the only side-by-side test found (Meshy, not Hunyuan) showed multi-view preserving raised surface relief that single-image "averages" away. No Hunyuan- or TRELLIS-specific controlled test was found.

### Cited Findings
- Hunyuan3D-2mv processes `front/left/back/right` each through the same 512→518 path and concatenates `num_views × tokens` with per-view embeddings — [preprocessors.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/preprocessors.py); [conditioner.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/models/conditioner.py); ComfyUI native multi-view node adds a 1D sinusoidal positional embedding over `arange(4)` and concatenates — [nodes_hunyuan3d.py](https://github.com/comfyanonymous/ComfyUI/blob/master/comfy_extras/nodes_hunyuan3d.py). ComfyUI docs: "multiple view images are not mandatory… you can use only the front view image" — [docs.comfy.org (snippet)](https://docs.comfy.org/tutorials/3d/hunyuan3d-2).
- Meshy test (HackerNoon, Observed): "single-image generation does not fail by breaking things. It fails by averaging them… patches, decals, and rivets compress toward the base surface in single-image output, while multi-view output keeps its standoff" — [HackerNoon](https://hackernoon.com/i-ran-the-same-anime-character-through-meshy-multiview-and-single-image-3d).
- Vendor claims: Segmind "better consistency and accuracy… compared to single-image-based methods" (marketing) — [Segmind Hunyuan3D-2mv](https://www.segmind.com/models/hunyuan3d-2mv); Scenario: multi-view 2.0 "detailed object modeling from limited views, using up to 4 reference images… slower" — [Scenario](https://help.scenario.com/en/articles/comparison-of-hunyuan-models).
- Hosted Hunyuan 3.1 via 3D AI Studio accepts up to 8 views (front, left, right, back, top, bottom, left_front, right_front), +20 credits — [Tencent Hunyuan API doc (snippet)](https://www.3daistudio.com/Platform/API/Documentation/3d-generation/tencent-hunyuan).
- Pixal3D multi-view: views "never cropped or rescaled"; first view canonical front — [Pixal3D README](https://github.com/TencentARC/Pixal3D).
- TRELLIS.2 README mentions no multi-image support (single image example) — [TRELLIS.2 README](https://github.com/microsoft/TRELLIS.2/blob/main/README.md); TRELLIS 1 added multi-image conditioning 2024-12-18 — [TRELLIS README](https://github.com/microsoft/TRELLIS/blob/main/README.md).

### Inferences
- Given fixed per-view conditioning resolution, the way to "spend" a high-resolution master is to split it into orthographic views (and, for Hunyuan 3.1 hosted, up to 8 views) rather than feed a single stitched sheet — each view then contributes its own ~518²/1024² of information.
- A stitched multi-region "master sheet" fed as one image would be treated as a single object by the recenter/bbox logic (all regions inside one bbox → each region tiny after the 512/518 resize) — worst case for detail (Inferred from the recenter code).

### Gaps
- No controlled Hunyuan3D-2mv vs 2.0 single-view detail comparison was found; the Meshy test is a different model.

## Key Question 8: Shortest reliable practical tests for what is undocumented

### Takeaway
Three short tests resolve the main unknowns: (1) a resolution-sweep on a local model with fixed seed to confirm the 512/518 ceiling empirically, (2) a 3D AI Studio upload-size probe (same image at 1024 px vs 8K, same seed/settings) plus an oversized file to find hard limits, and (3) a Blackwell smoke test of the texturing extensions (`import custom_rasterizer`) before investing in a full Hunyuan3D texture workflow.

### Cited Findings (procedural anchors)
- Hunyuan3D-2 exposes `octree_resolution`, `num_chunks`, `mc_level`, seed-controlled generation; ComfyUI native nodes fix `octree_resolution` default 256 and expose `VoxelToMesh` — [pipelines.py](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/hy3dgen/shapegen/pipelines.py); [nodes_hunyuan3d.py](https://github.com/comfyanonymous/ComfyUI/blob/master/comfy_extras/nodes_hunyuan3d.py).
- TRELLIS.2 `run()` seed default 42, `preprocess_image` downsizes to 1024 — [trellis2_image_to_3d.py](https://github.com/microsoft/TRELLIS.2/blob/main/trellis2/pipelines/trellis2_image_to_3d.py).
- kijai wrapper requires `custom_rasterizer_kernel*.pyd` + `custom_rasterizer` folder in site-packages for texturing — [kijai README](https://github.com/kijai/ComfyUI-Hunyuan3DWrapper).
- 3D AI Studio documented soft limits: ≤50 MB, PNG/JPG/JPEG — [troubleshooting](https://docs.3daistudio.com/troubleshooting).

### Inferences (proposed tests — not run)
1. **Resolution-sweep (local, ~15 min):** same transparent-background object image at 512, 1024, 2048, 4096 px long side → Hunyuan3D-2 (or TRELLIS.2 native) with identical seed/steps/`octree_resolution` → compare meshes (e.g., Hausdorff/Chamfer in MeshLab or trimesh) and rendered normals. If 1024→4096 outputs are near-identical while 512→1024 differ slightly, the documented ceiling is confirmed.
2. **3D AI Studio probe (~3 generations, Rapid edition cheapest at 35 credits):** upload the 8K master and a 1024-px downscale with the same seed/settings per model (Hunyuan Rapid, TRELLIS.2); compare outputs; then upload a >50 MB PNG and a 12k×12k PNG to find hard dimension/size errors; also test one oversized base64 payload via the API to detect a payload cap. Record whether the web app previews a cropped/resized thumbnail (hints at server-side preprocessing).
3. **Blackwell texturing smoke test (~30 min):** in the ComfyUI venv run `python -c "import torch; print(torch.cuda.get_arch_list())"` (must include `sm_120`) then `python -c "import custom_rasterizer"` after installing kijai's wheel; if ImportError or "no kernel image", attempt source build with `TORCH_CUDA_ARCH_LIST=12.0` from `hy3dgen/texgen/custom_rasterizer`; fall back to the WinPortable cu129 bundle, which lists Blackwell support.
4. **TRELLIS.2 16 GB fit test:** native workflow with structure grid 32, `target_resolution` 1024, remesh off; watch peak VRAM; then try 64 / 1536 to reproduce the community OOM boundary.

### Gaps
- No published test of any of the above on an RTX 5070 Ti specifically (one Linux success report for TRELLIS.2 standalone on a 5070 Ti exists in [TRELLIS.2 #143](https://github.com/microsoft/TRELLIS.2/issues/143); none for Windows/ComfyUI).
