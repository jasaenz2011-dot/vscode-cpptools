## KQ1. Comparison of the five approaches (AI image-to-3D + cleanup; Blender-native with AI assistance; hybrid blockout; local Hunyuan3D/TRELLIS in ComfyUI; other alternatives)

### Takeaway
As of October 2026 no route produces a design-faithful, modular, deform-ready character without a human topology/UV pass; the evidence favours a **hybrid**: AI reconstruction (cloud Tripo/Meshy, or local Hunyuan3D 2.x / TRELLIS.2 on the 16 GB card for shape only) to get volumes and a sculpt/blockout reference fast, then native Blender modelling of the hard-surface shell, retopology, UVs and rigging where control matters. LLM/MCP agents are credible for repeatable scripting (cleanup, export, batch bake) and for right-angled hard-surface primitives, not for organic/character form.

### Cited Findings

**(1) AI image-to-3D then Blender cleanup**
- Tripo's retopology API defaults to a "smart" algorithm (v2.0) with a basic decimation mode (v1.0); quad output is a boolean both modes support; texture baking defaults on; accepted inputs GLB/GLTF/FBX/OBJ/STL up to 150 MB — [Tripo developer docs (excerpt)](https://developers.tripo3d.com/en/docs/mesh-decimate.md). **Documented (excerpt)**
- The ComfyUI Tripo Retopology node says that with quad enabled the maximum face limit is 10,000 quads instead of 20,000 triangles and the result is delivered as FBX; Scenario's guide says the face limit is a 1k–20k *target*, and quad results can land slightly above it — [ComfyUI docs TripoRetopologyNode (excerpt)](https://docs.comfy.org/built-in-nodes/TripoRetopologyNode); [Scenario Tripo Family guide (excerpt)](https://help.scenario.com/articles/4692888910-tripo-family-the-complete-guide). The two figures conflict; check the live API reference. **Documented (excerpt), conflicting**
- A third-party review reported "Smart Low Poly is a blunt instrument on hands and faces"; another says Smart Mesh P1.0 "does not fully replace manual cleanup for hero assets" — [Neural4D Tripo 3.1 review (excerpt)](https://newsletter.neural4d.com/p/tripo-3-1-model-review). **Observed**
- A Tripo tester reported an AI-generated armoured warrior came out at ~1.9 million faces — [LevelUp/Medium Tripo Smart Mesh article (excerpt)](https://levelup.gitconnected.com/tripo-ais-new-smart-mesh-feature-60-faster-33-cheaper-c9278f0579f3). **Observed (blog)**
- Meshy's pipeline includes Remesh (polycount optimisation, watertight geometry; quad or triangle with target polycount per Scenario), Unwrap UV (separate step; recommended before texturing when seams/distortion appear), and AI Texturing that outputs albedo, normal, roughness, metallic, optional 2K/4K — [Meshy glossary (excerpt)](https://docs.meshy.ai/en/webapp/glossary); [Meshy concepts (excerpt)](https://docs.meshy.ai/en/webapp/concepts); [Meshy AI texturing (RU docs, excerpt)](https://docs.meshy.ai/ru/webapp/guides/3d-model/ai-texturing). **Documented (excerpt)**
- Meshy's multi-image mode applies "automatic image enhancement and lighting removal" to inputs before reconstruction; the API exposes `decimation_mode` (adaptive decimation polycount), HD texture and emission maps (meshy-6/latest only) — [Runware Meshy 6 docs (excerpt)](https://runware.ai/docs/models/meshy-6); [Meshy API changelog (excerpt)](https://docs.meshy.ai/api/changelog). **Documented (excerpt)**
- A polycount thread (2025–26) states Meshy/Tripo outputs are "usable for props and background assets" but "the trouble starts between export and getting the asset into an engine", and asks whether anyone has an acceptable automated route for characters that must deform; one reply says Blender scripting got them close — [polycount: How are you actually handling AI-generated mesh cleanup](https://polycount.com/discussion/238705/how-are-you-actually-handling-ai-generated-mesh-cleanup-before-engine-handoff). **Observed (excerpt)**
- A vendor cleanup guide (Neural4D, 2026) lists the typical defects of Meshy/Tripo output — non-manifold geometry, inverted normals, "50,000+ unorganized triangles" — and the sequence audit → repair → reduce → fix normals → export prep — [Neural4D Blender cleanup guide (excerpt)](https://blog.neural4d.com/user-guide/ai-3d-model-blender-cleanup-complete-mesh-fix-guide-2026/). **Observed, vendor-authored**
- Comparative quality: Meshy's own compare page claims "Meshy 6 is preferred by 63.8% of professional evaluators" with no methodology — [Meshy compare (excerpt)](https://www.meshy.ai/it/compare). **Unverified (vendor)**
- Scenario's model comparison positions Tripo 2.5 for photorealistic single-object work and "Trellis 2 for complex topologies and stylized characters" — [Scenario: Comparing Generative 3D Models (excerpt)](https://help.scenario.com/en/articles/comparing-generative-3d-models/). **Observed (platform vendor opinion)**
- An independent six-model test (Sorceress) concluded "no single backend wins every test", scoring geometric fidelity and topology separately; it describes Rodin as strong on hard-surface assets — [Sorceress six-model test (excerpt)](https://sorceress.games/blog/rank-the-best-image-to-3d-model-ai-six-model-test). **(2) Native/procedural Blender with AI assistance (LLM scripting, blender-mcp)**
- ahujasid/blender-mcp (30.4k stars, 244 commits at check) gives the agent: object/material create-modify-delete, arbitrary Blender Python execution, a `look` tool returning viewport/camera/multi-angle/wireframe/X-ray/render views so the model can inspect its work, asset pulls from Poly Haven/Sketchfab/Poly Pizza, and AI model generation via Tripo, Hyper3D Rodin or Hunyuan3D; requires Blender 3.0+/Python 3.10+; PyPI package renamed to `mcp-for-blender` — [ahujasid/blender-mcp README](https://github.com/ahujasid/blender-mcp). **Documented**
- The same README warns `execute_blender_code` runs arbitrary Python, the addon socket has no authentication/encryption (keep on localhost or SSH tunnel), safe mode is off by default (`BLENDER_MCP_SAFE_MODE=1`), complex requests may need splitting and can time out, and only one MCP server instance should run at a time — [ahujasid/blender-mcp README](https://github.com/ahujasid/blender-mcp). **Documented**
- Practitioner reviews: it "handles basic scene assembly … though results are rough and complex scripts often need several retries"; it does well on "geometry with clear right angles, like stairs, railings, and modular walls, because primitives and booleans are the right tools", and reviewers say it "struggles with organic or character work" and "won't replace artistic judgment" — [MindStudio: Claude Blender MCP real-world performance (excerpt)](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance); [yuv.ai BlenderMCP write-up (excerpt)](https://yuv.ai/blog/blender-mcp). **Observed (blogs)**
- A competing project argues that asking the model to write raw bpy "breaks down where production work gets difficult" — [3D AI Studio blender-mcp comparison (excerpt)](https://www.3daistudio.com/3d-generator-ai-comparison-alternatives-guide/blender-mcp). **Unverified (competitor)**

**(3) Hybrid: reconstruction as blockout/sculpt reference**
- Tripo's own guidance for AI character models recommends automated retopology for a first pass, then export to Blender/Maya for "targeted manual refinement" where test poses reveal problems — [Tripo blog: retopo an AI character model for animation (FR, excerpt)](https://www.tripo3d.ai/fr/blog/retopo-an-ai-character-model-for-animation). **Observed (vendor)**
- An artist write-up says the AI quad mesh is "an excellent starting point that they then refine by hand, especially around the eyes and mouth"; another notes "hard caps and no control over where density goes" as limits of smart retopo — [search excerpts from Tripo polycount guide](https://www.tripo3d.ai/blog/explore/smart-mesh-polycount-benchmarking-across-asset-types) and [Tripo manual editing guide](https://www.tripo3d.ai/game-development/master-manual-editing-and-refining-workflows-for-ai-generated-3d-game-assets). **Observed (vendor blog)**
- A CharacterGen tutorial recommends auditing AI meshes in Blender for non-manifold geometry, overlapping vertices and excessive triangulation and keeping an untouched copy of the AI output — [aiindigo CharacterGen tutorial (excerpt)](https://aiindigo.com/tutorials/getting-started-with-charactergen-turn-2d-art-into-rigged-3d-models). **Observed**

**(4) Local Hunyuan3D / TRELLIS in ComfyUI on a 16 GB RTX 5070 Ti**
- Hunyuan3D-2 (2.0 line, incl. 2mv multiview and mini variants): "about 6 GB" VRAM for shape, "about 16 GB" for shape + texture; 2mv is a 1.1B multiview image-to-shape model released 2025-03-18; Fast (guidance-distilled) variants roughly halve DiT time — [Tencent-Hunyuan/Hunyuan3D-2 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2). **Documented**

- The hy3dpaint README (via search excerpt) states PBR textures come out at 512 or 768 and recommends at least 21 GB VRAM for `max_num_view=6, resolution=512` — [Hunyuan3D-2.1 hy3dpaint README (excerpt)](https://huggingface.co/spaces/tencent/Hunyuan3D-2.1/blob/main/hy3dpaint/README.md). **Documented (excerpt)**
- The ComfyUI wrapper (visualbruno/ComfyUI-Hunyuan3d-2-1) is tested on Windows 11, Python 3.12, Torch ≥2.6 + cu126, ships Windows wheels for the custom rasteriser/differentiable renderer and an optional xatlas patch for UV unwrapping high-poly meshes; it gives no VRAM figures — [visualbruno/ComfyUI-Hunyuan3d-2-1 README](https://github.com/visualbruno/ComfyUI-Hunyuan3d-2-1). - Hunyuan3D 3.0 is described as the production model (1536³ geometry) delivered via Tencent Cloud API and the Hunyuan 3D engine (global launch 25 Nov 2025); I found no source confirming open weights for 3.0 or any "3.1" release — [comfyui-wiki Hunyuan3D overview (excerpt)](https://comfyui-wiki.com/en/models/hunyuan3d); [aiindigo 2.1 review 2026 (excerpt)](https://aiindigo.com/blog/comprehensive-review-hunyuan3d-2-1-in-2026). **Documented (excerpt) / Gap**

- Hunyuan3D-Omni (3.3B, released 2025-09-25, ~10 GB VRAM) adds control signals — point cloud, voxel, **bounding box**, and **skeletal pose** — to image-to-shape via one unified control encoder; it is an image-to-shape model (texture output not stated) — [Tencent-Hunyuan/Hunyuan3D-Omni README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Omni); [arXiv 2509.21245 (excerpt)](https://arxiv.org/html/2509.21245v1). **Documented**

**(5) Other alternatives with evidence**
- Blender's own tools for the hard-surface shell (boolean/bevel/modifiers) are implicitly where blender-mcp reviewers say LLM scripting works best (right-angled primitives/booleans) — [MindStudio review (excerpt)](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance). **Observed**
- Hyper3D Rodin is reachable from blender-mcp and is described as strong on hard-surface/architectural assets in the Sorceress test — [blender-mcp README](https://github.com/ahujasid/blender-mcp); [Sorceress (excerpt)](https://sorceress.games/blog/rank-the-best-image-to-3d-model-ai-six-model-test). **Documented / Observed**

### Inferences
- Time cost ordering for *a first look*: (4)/(1) minutes per part; (3) hours; (2) hours-to-days. Time cost ordering for *a final, deform-ready, design-faithful modular asset* collapses toward the same manual retopo/UV/rig budget for all routes, because every source (Tripo's own blog, polycount, Neural4D, tspi.at) reports the mandatory cleanup pass; the saving from AI is in volume discovery and texture starting points, not in topology. **Inferred**
- Controllability/fidelity to a specific 2D design is lowest for single-image AI reconstruction and highest for native modelling; Hunyuan3D-Omni's bounding-box and pose conditioning and Tripo/Meshy multi-view inputs are the only documented ways to push AI generation toward fixed proportions. **Inferred from documented controls**
- On a 16 GB RTX 5070 Ti: Hunyuan3D-2 (shape+texture ≈16 GB — marginal) and 2mv/mini shape-only (≈6–10 GB) are realistic; Hunyuan3D-2.1 PBR texturing (21 GB) and TRELLIS.2 (24 GB stated, Linux only) are not reliably local without FP8/low-VRAM community modes that nobody has documented as working at 16 GB. Local use is therefore "shape and blockout" rather than "finished PBR character". **Inferred**
- Hard-surface robot shells are the one character sub-problem where LLM-scripted Blender modelling (primitives, booleans, bevels, mirror) plausibly beats AI reconstruction on fidelity, per the right-angle/boolean observations; the oval faceplate and organic silicone sleeves are not. **Inferred**

### Gaps
- No controlled benchmark of these generators on *stylized robot characters* with fixed proportions exists in what I found; Sorceress/Scenario comparisons are informal.
- No source confirms TRELLIS.2 or Hunyuan3D-2.1 texturing running on 16 GB; FP8/low-VRAM claims are undocumented.
- Hunyuan3D license terms (geographic restrictions were alleged by Meshy's compare page) were not read; LICENSE file fetch failed.

## KQ2. Preserving silhouette/proportions across independently generated parts; whole-first vs parts-first vs body-plus-shells; what part-segmentation features can and cannot do

### Takeaway
Part-segmentation/completion tools (Tripo Segmentation v1/v2 + Complete Mesh Parts, Hunyuan3D-Part P3-SAM + X-Part, PartCrafter, HoloPart) can split or regenerate *a single generated object* into named, closed parts, which is useful for separating shell from faceplate or arm from torso on one reconstruction; none of them documents a mechanism for making *independently generated* variants share dimensions. The documented levers for cross-part consistency are Hunyuan3D-Omni bounding-box/pose conditioning, multi-view input from one fixed turnaround, and conventional DCC practice (one master body, orthographic reference planes, shrinkwrap/socket conventions) — so "generate the whole character once, segment, then derive variant shells from the master body" is the evidence-consistent order.

### Cited Findings
- Tripo Smart Segment (ComfyUI partner node): "splits a 3D model into semantically meaningful parts and gives each part a name"; works on an existing model (task ID) or generates then segments; GLB input only (FBX quads must be converted first); ~180 s; errors if Tripo returns incomplete segmentation; output task_id feeds Complete Mesh Parts, Retopology, Texture model, Convert model; ~US$0.85 (image input) / $0.55 (model input) — [ComfyUI docs TripoSmartSegmentNode (excerpt)](https://docs.comfy.org/built-in-nodes/TripoSmartSegmentNode). Outputs include `part_names`, `parts`, `mask`, `GLB` per the localized pages — [JA page (excerpt)](https://docs.comfy.org/ja/built-in-nodes/TripoSmartSegmentNode.md). **Documented (excerpt)**
- Tripo Segmentation v2 (Beta, model id v2.0-20260430): granularity `simple|balanced|detailed`, `split_by_connectivity` (default true), optional `ref_image` to guide semantic analysis — when set, granularity and connectivity are ignored; inputs ≤150 MB GLB/GLTF/FBX/OBJ/STL — [Tripo developers mesh-segment (excerpt)](https://developers.tripo3d.com/en/docs/mesh-segment.md); [Scenario Tripo Segmentation essentials (excerpt)](https://help.scenario.com/articles/9861107995-tripo-segmentation-the-essentials). v1 is geometry-based/automatic — same Scenario page. **Documented (excerpt)**
- Tripo retopology's `part_names` parameter "is not supported by v1.0" (basic decimation) — [Tripo developer docs (excerpt)](https://developers.tripo3d.com/en/docs/mesh-decimate.md), implying smart retopo can operate per named part. **Documented (excerpt)**
- Hunyuan3D-Part: P3-SAM (native 3D segmentation, "can handle any input mesh") outputs semantic features, part segmentations and part bounding boxes; X-Part then "generates the complete parts"; X-Part is recommended for scanned/AI-generated meshes (Hunyuan3D 2.5/3.0); the public X-Part is a "light version" with the full version only in Hunyuan3D-Studio; VRAM, max parts and license terms are not stated — [Tencent-Hunyuan/Hunyuan3D-Part README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Part); papers arXiv 2509.06784 (P3-SAM) and 2509.08643 (X-Part). **Documented**
- PartCrafter (NeurIPS 2025, MIT, fully open-sourced 2025-07-13): generates multiple parts from one RGB image in one pass without a prior segmentation step, including parts not visible in the input; `--num_parts` is set explicitly or suggested by a VLM; inference needs "at least 8GB VRAM"; training configs are `mp8`/`mp16`; trained on Objaverse renders so real photos may need style transfer; Windows via community fork — [wgsxm/PartCrafter README](https://github.com/wgsxm/PartCrafter); [arXiv 2506.05573](https://arxiv.org/html/2506.05573v1). Scenario's product wrapper describes 2–16 parts — [Scenario PartCrafter essentials (excerpt)](https://help.scenario.com/en/articles/partcrafter-the-essentials/). **Documented**
- HoloPart (ICLR 2026 poster, MIT, April 2025): "amodal" part completion — takes a mesh already segmented (SAMPart3D/SAMesh recommended, per-face labels in `mask.npy`) and completes each part into full geometry; integration of segmentation is "Coming Soon" — [VAST-AI-Research/HoloPart](https://github.com/VAST-AI-Research/HoloPart); [arXiv 2504.07943](https://arxiv.org/abs/2504.07943v1). **Documented**
- Hunyuan3D-Omni: "Generate 3D models constrained by 3D bounding boxes" and "Create 3D human models with specific skeletal poses"; ~10 GB VRAM — [Hunyuan3D-Omni README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Omni). **Documented**
- Tripo multiview-to-model requires the front image plus at least one of left (90°), back (180°), right (270°) — [Scenario Tripo docs (excerpt)](https://docs.scenario.com/docs/3d-model-generation-tripo-ai); [ComfyUI TripoMultiviewToModelNode (excerpt)](https://www.runcomfy.com/comfyui-nodes/ComfyUI/tripo-multiview-to-model-node). Meshy multi-image accepts 1–4 (webapp docs say 2–8) images, ordered front, back, left, right, with plain background and similar framing — [Runware Meshy 6 (excerpt)](https://runware.ai/docs/models/meshy-6); [Meshy image-to-3D docs (excerpt)](https://docs.meshy.ai/en/webapp/image-to-3d). **Documented (excerpt)**
- Ready Player Me's outfit pipeline is a documented "common body plus garments" modular scheme: creators keep the template armature and UV layout, remove body geometry hidden by clothing, and keep each mesh to one material with fixed per-slot triangle budgets — [RPM Fullbody Outfits (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-outfits). **Documented (excerpt)**
- A third-party API page lists "breaking a single model into reusable components for asset libraries" and "identifying body parts for skeletal rigging" as segmentation use cases — [3D AI Studio Tripo segmentation docs (excerpt)](https://www.3daistudio.com/Platform/API/Documentation/segmentation/tripo). **Unverified (vendor)**

### Inferences
- What segmentation *can* do for this project: take one good whole-robot reconstruction and split it into head/faceplate/torso/upper-arm/forearm/hand/leg/foot with named, closed parts (Tripo Complete Mesh Parts, X-Part, HoloPart). What it *cannot* do: guarantee that a separately generated silicone arm has the same length, joint positions or bounds as the robotic arm — nothing in any doc addresses cross-generation dimensional consistency. **Inferred**
- The evidence-consistent order is: (a) generate/sculpt a single **master body** (whole character, single pose, from the fixed turnaround); (b) segment it into parts to establish the canonical part bounds, pivots and seams; (c) author each variant shell (robotic/silicone/frosted) *from the same part*, by re-sculpting, shrinkwrapping or re-skinning the master part rather than regenerating — this is exactly the RPM "keep the template body/armature, replace surface geometry" pattern. Regenerating variant parts with AI is acceptable only as a sculpt reference, or with Hunyuan3D-Omni bbox conditioning to the master part's bounding box. **Inferred**
- "Kitbash to a master skeleton": AI parts should be snapped to the master armature's joint positions (bone heads/tails = attachment points) and clipped to the master part's bounding box; limb variants that must be interchangeable should be modelled inside identical bounding volumes with identical joint locations. No source documents this phrase; it is standard modular-character practice extrapolated from RPM/VRM conventions. **Inferred**
- Orthographic reference planes (front/side/back image empties in Blender) remain the control for native/hybrid modelling; multi-view inputs are the AI-side equivalent. **Inferred**

### Gaps
- I could not read Tripo's "Complete Mesh Parts" documentation (what it closes, whether it regenerates occluded regions).
- No practitioner account of a *modular* multi-variant character built with Tripo/Meshy/Hunyuan was found (polycount thread is the closest, and it is a question not a solution).
- Hunyuan3D-Part VRAM/part-count limits undocumented.

## KQ3. Obtaining consistent front/side/back references; multi-view generation in ComfyUI; does multi-view beat one large image?

### Takeaway
Multi-view input is documented by Tripo, Meshy and Hunyuan3D-2mv and is consistently positioned by vendors as better for back/side fidelity, but no independent side-by-side exists; the practical risk is that inconsistent generated views distort the result, so consistency of the sheet matters more than view count. In ComfyUI the current options are dedicated turnaround LoRAs (FLUX Kontext; CharacterSheet for FLUX.2 Klein 9B / Krea 2, July 2026), MV-Adapter (SDXL, 6 views, ~14 GB), and Tripo's own image-to-multiview API.

### Cited Findings
- Hunyuan3D-2mv in ComfyUI natively: the workflow expects front, left, back, right images, but "multiple view images are not mandatory … you can use only the front view image"; the ComfyUI docs state ComfyUI does not yet support texture/material generation for this model (a 2025 blog claims PBR support — possible doc lag) — [ComfyUI Hunyuan3D-2 tutorial (excerpt)](https://docs.comfy.org/tutorials/3d/hunyuan3d-2); [comfy.org blog (excerpt)](https://blog.comfy.org/p/hunyuan3d-20-and-muitiview-native). **Documented (excerpt)**
- Hunyuan3D-2mv model card: 1.1B multiview image-to-shape, 2025-03-18; mv-Turbo/mv-Fast distilled variants — [Hunyuan3D-2 README](https://github.com/Tencent-Hunyuan/Hunyuan3D-2). **Documented**
- Tripo image-to-multiview API: input file token or public URL (PNG/JPEG/WebP), recommends a clearly visible subject on a clean background, outputs front/left/back/right URLs; ComfyUI "Tripo: Edit Multiview" applies a separate text instruction per view — [Tripo developers image-to-multiview (ZH, excerpt)](https://developers.tripo3d.com/zh/docs/generation-image-to-multiview); [ComfyUI TripoEditMultiviewNode (excerpt)](https://docs.comfy.org/built-in-nodes/TripoEditMultiviewNode.md). **Documented (excerpt)**
- MV-Adapter (ICCV 2025, Apache-2.0): SDXL/SD2.1 adapters, 768 px on SDXL, 6-view configs (also 2/3/4 views for single-image input), image-to-multiview "requires about 14G GPU memory", geometry-guided texture variants (image+geometry SDXL >16 GB; SD2.1 <10 GB), ComfyUI support via ComfyUI-MVAdapter — [huanngzh/MV-Adapter README](https://github.com/huanngzh/MV-Adapter). The IG2MV ComfyUI node is hard-coded to exactly 6 views — [RunComfy ComfyUI-IG2MV (excerpt)](https://www.runcomfy.com/comfyui-nodes/ComfyUI-IG2MV). **Documented**

- FLUX Kontext character-turnaround LoRA workflows: one illustrated character → five poses on white background; "works best with full-body shots of illustrated or stylized characters, not real photos or tight head shots" — [RunComfy Flux Kontext turnaround LoRA (excerpt)](https://www.runcomfy.com/comfyui-workflows/flux-kontext-character-turnaround-sheet-lora). **Observed (workflow page)**
- Comfy.org "360 Full-body Turnaround" template uses a Gemini 3 Pro Image Preview API node then ImageStitch — [comfy.org template (excerpt)](https://www.comfy.org/workflows/templates-character_sheet-c70904777c65). - Scenario's multi-view tutorial: reference images should share the same aspect ratio, since inconsistent proportions can distort the model — [Scenario Use Multi-View (excerpt)](https://help.scenario.com/en/articles/use-multi-view-for-better-3d-models). - No head-to-head benchmark of 2mv multiview vs single view on back-side detail was found. **Gap**

### Inferences
- For a *symmetric hard-surface robot defined by a 2D concept*, the highest-leverage reference is a clean orthographic 3-view (front/side/back) produced from the concept with a turnaround LoRA or Tripo image-to-multiview, then **hand-corrected in 2D** for proportion consistency before feeding Tripo/Meshy/2mv; the vendor warnings about distortion from inconsistent views imply that a slightly imperfect but consistent sheet beats a richer but inconsistent one. **Inferred**
- The CharacterSheet LoRA's human-centric training is a stated risk for a robot; FLUX Kontext stylized-character guidance is a better fit on paper. Neither has been shown on robots. **Inferred**
- One large single image is adequate for the *blockout* use (approach 3) where only front silhouette and volumes are needed; multi-view earns its cost when the AI mesh will be kept (approach 1). **Inferred**

### Gaps
- Qwen-Image-Edit / Zero123++ turnaround specifics were not reached before the search budget ended.
- No evidence on multi-view performance specifically for translucent/frosted subjects.

## KQ4. Avoiding baked reflections, lighting, specular and transparency being read as geometry/albedo

### Takeaway
Vendors and help centres agree: feed evenly lit, matte, opaque, single-subject, plain-background images; hard shadows become geometry and highlights/reflections become texture; glass/clear plastic is read "through" rather than as a surface. Meshy applies automatic lighting removal; Hunyuan3D-2.1 handles illumination via training-time consistency rather than an explicit delighting pass; TRELLIS.2 outputs an opacity channel but exports opaque by default. Supplying an opaque matte proxy of the frosted shell and adding translucency in the material later is the evidence-consistent strategy.

### Cited Findings
- "Hard directional light creates deep shadows that the AI might interpret as part of the object's geometry, leading to weird lumps or holes"; the generator "can't tell the difference between 'this side is darker because the object is curved' and '… because the light source is on the other side'" — [Sloyd: Preparing flat images for better 3D results (excerpt)](https://www.sloyd.ai/blog/preparing-flat-images-for-better-3d-results). **Observed (vendor)**
- On-camera flash creates "harsh highlights (specular hotspots) that confuse the texture generation"; mirrors and polished chrome make "the AI think the reflection is actually painted onto the object"; glass and clear plastic are hard "because the AI sees through them rather than seeing the surface" — [PrintPal image-to-3D best practices (excerpt)](https://printpal.io/wiki/image-to-3d-best-practices). **Observed (vendor)**
- Scenario: prefer stylized artwork with clear edges and one subject; "avoid extreme shadows or multiple light sources"; run Enhance first on images under 1024² — [Scenario Image-to-3D best practices (excerpt)](https://help.scenario.com/en/articles/image-to-3d-best-practices/). **Documented (excerpt)**
- Even lighting is the goal, not shadowless: sources note some form-defining shading helps depth reading — [search synthesis of Sloyd/PrintPal pages](https://www.sloyd.ai/blog/common-mistakes-when-creating-3d-models-from-images). **Observed**
- Meshy: multi-image mode applies "automatic image enhancement and lighting removal" before reconstruction; Image Enhancement can be turned off for high-quality inputs — [Runware Meshy 6 (excerpt)](https://runware.ai/docs/models/meshy-6); [Meshy image-to-3D docs (excerpt)](https://docs.meshy.ai/en/webapp/image-to-3d). **Documented (excerpt)**
- Neural4D claims "standard projection permanently prints the dark shadow underneath the subject and the bright glares on top into the texture" and proposes intrinsic decomposition — [Neural4D how-to (excerpt)](https://www.neural4d.com/how-tos/how-to-solve-baked-shadows-and-lighting-issues). **Unverified (vendor)**
- Hunyuan3D-2.1's texture model is dual-branch (albedo + metallic-roughness sharing attention) and is trained with a consistency loss across renders under different lighting so material estimates stay stable — [alphaXiv overview of 2506.15442 (excerpt)](https://alphaxiv.org/overview/2506.15442v1). No explicit inference-time delighting step is documented. **Documented (secondary summary)**
- TRELLIS.2 materials include Opacity, but "the GLB exports in OPAQUE mode by default, so the alpha channel must be connected manually in 3D software" — [microsoft/TRELLIS.2 README](https://github.com/microsoft/TRELLIS.2). **Documented**
- Meshy help centre: use a clear front-facing image on a plain background, 1:1 aspect for generated inputs; PNG/JPG/WebP ≤20 MB — [Meshy help (excerpt)](https://intercom.help/meshy/en/articles/9996860-how-to-use-meshy-image-to-3d). **Documented (excerpt)**

### Inferences
- "Material-neutral" reference variants for this robot: render/paint the concept with the frosted shell as an **opaque, matte, mid-grey/white** surface, internals removed, no rim light, no emissive sole, soft two-sided fill, neutral white balance, plain background; keep a second "look" sheet for texture/material authoring only. This directly addresses each documented failure mode (shadows→geometry, hotspots/reflections→albedo, transparency→see-through). **Inferred**
- Because frosted plastic over internals reads as a surface *plus* faint interior structure, any AI generator will either flatten the internals into the shell albedo or hallucinate surface relief; so the internals should never be in the geometry reference. **Inferred**
- Vendor PBR output (Meshy/Tripo/Hunyuan 2.1) is a starting albedo at best; baked shading in generated albedo should be expected and checked under a neutral HDRI, and the shell's roughness/transmission authored by hand. **Inferred**

### Gaps
- No source quantifies how much residual shading remains in Meshy's "lighting removal" or Hunyuan 2.1 albedo.
- No documented test of image-to-3D on frosted/translucent subjects specifically.

## KQ5. Authoring frosted plastic with visible internals for a browser/mobile asset (authoring strategy only)

### Takeaway
Real transmission (KHR_materials_transmission/volume) is documented as one of the most expensive glTF material features on phones and has forced a per-material switch-off to recover frame rate; the game-art precedent for "translucent housing with something inside" is an opaque shell with the interior painted/baked into albedo and driven by emissive, optionally with a cheap inner mesh. Author the frosted look as a baked, opaque-first material with optional transmission upgrade for capable devices.

### Cited Findings
- KHR_materials_transmission is specified as a thin-surface approach for "the simplest and most common use cases for optical transparency: infinitely-thin materials with no refraction, scattering, or dispersion"; combined with KHR_materials_volume it may be used for thicker, refractive materials — [Khronos KHR_materials_transmission spec](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_transmission/); [glTF-Transform docs](https://gltf-transform.dev/modules/extensions/classes/KHRMaterialsTransmission). **Documented**
- Three.js forum: transmission/refraction "had a large effect on frame rate on a smartphone" while fine on desktop; transmission forces MeshPhysicalMaterial, "each extension adds features and cost", making apps fragment-shader-bound on mobile; switching transmission off on one material restored frame rate; mitigations: swap to cheaper materials after load, disable the extension in the loader on low-end devices, or re-export without it — [three.js discourse: optimizing glTF FPS low](https://discourse.threejs.org/t/issue-with-optimizing-my-gltf-file-fps-low/65775); [three.js discourse: disabling KHR extensions](https://discourse.threejs.org/t/disabling-specific-khr-extensions/29514). **Observed (forum, Three.js not Babylon)**
- Needle forum: the extension renders glass-like materials "in a way that is compatible with mobile devices" but keep the shader lightweight — [Needle forum: Glass shader](https://forum.needle.tools/t/glass-shader/2444). **Observed**
- Fake-translucency precedent (UE5 Fortnite "Emma Frost" diamond skin): "reduce the Base Color, then layer various computed values into the Emissive channel to create the illusion of translucency", explicitly to avoid real transparency as a "performance disaster" — [80.lv article (excerpt)](https://80.lv/articles/how-to-set-up-emma-frost-style-opaque-diamond-skin-from-fortnite-in-ue5/). **Observed**
- Light inside a translucent housing: Marmoset forum answer recommends an emissive map "so you can customize it to have any falloff and color you like" — [polycount/Marmoset thread (excerpt)](https://polycount.com/discussion/comment/2702683). **Observed**
- Silent Hill 2 plastic sheeting analysis: the plastic is largely opaque with the occluded wall applied as its texture — [80.lv (excerpt)](https://80.lv/articles/the-secret-behind-silent-hill-2-s-transparent-plastic-sheeting). **Observed**
- Frosted glass via blur+noise of a rendered image "works well on fundamentally flat geometry" — [gamedev.net thread (excerpt)](https://gamedev.net/forums/topic/281457-translucent-subsurface-scattering-approximation/). **Observed (old)**
- TRELLIS.2 can emit an opacity channel (see KQ4) — [microsoft/TRELLIS.2](https://github.com/microsoft/TRELLIS.2). **Documented**

### Inferences
- Authoring plan consistent with the evidence: (a) model the **shell** as a closed, opaque-capable mesh and a **low-poly inner mechanism** mesh (or none); (b) bake the inner mechanism, as seen through a frosted layer, into the shell's **albedo + emissive** (Blender: render internals through a rough-transmission shader to the shell UVs, or composite in 2D) so the base tier is pure opaque PBR; (c) optionally keep the inner mesh and a KHR_materials_transmission/volume shell as an upgrade tier, with the engine-side fallback the Babylon researcher covers. The frosted "diffusion" is thereby a texture, which is also what makes variant swaps (silicone vs robotic vs frosted) texture-driven as the brief wants. **Inferred**
- Illuminated sneaker sole = emissive texture + optional variation masks, not transmission. **Inferred**

### Gaps
- No Babylon.js-specific transmission numbers (out of scope here).
- No measured mobile cost of a single-material transmission shell at avatar scale.

## KQ6. Do converters output separate components, or must separation be authored afterwards?

### Takeaway
Default image-to-3D output from Tripo/Meshy/Hunyuan3D/TRELLIS is a single fused mesh; separate components come only from (a) explicit segmentation/completion steps (Tripo Segment + Complete Mesh Parts, Hunyuan3D-Part, HoloPart), (b) part-native generators (PartCrafter), or (c) manual Blender separation (Separate by Loose Parts/Selection, booleans, re-sculpt). Segmented output is still ungraded for seams, overlaps and interior faces, so a Blender pass is still needed.

### Cited Findings
- Tripo Segment node returns "the segmented model in GLB format with a comma-separated list of part names" — [ComfyUI TripoSegmentNode (excerpt)](https://docs.comfy.org/built-in-nodes/TripoSegmentNode). Tripo Smart Segment outputs `parts`, `mask`, `part_names`, `GLB`, and errors on incomplete segmentation — [ComfyUI TripoSmartSegmentNode (excerpt)](https://docs.comfy.org/built-in-nodes/TripoSmartSegmentNode). **Documented (excerpt)**
- Hunyuan3D-Part: P3-SAM gives segmentations + part bounding boxes; X-Part "generates the complete parts" (whether exported as separate files is not stated) — [Hunyuan3D-Part README](https://github.com/Tencent-Hunyuan/Hunyuan3D-Part). **Documented**
- PartCrafter "jointly generates multiple parts and objects from a single RGB image in one shot" — [wgsxm/PartCrafter](https://github.com/wgsxm/PartCrafter). **Documented**
- HoloPart requires an already-segmented mesh and completes each part — [HoloPart README](https://github.com/VAST-AI-Research/HoloPart). **Documented**
- Hunyuan3D-2/2.1 and TRELLIS.2 pipelines document a single trimesh/GLB output per image, with no part output — [Hunyuan3D-2](https://github.com/Tencent-Hunyuan/Hunyuan3D-2); [TRELLIS.2](https://github.com/microsoft/TRELLIS.2). **Documented (absence)**
- Tripo's own blog on baking says to "remove any internal faces, duplicate vertices, or non-manifold edges on both meshes before baking" — [Tripo texture baking guide (excerpt)](https://www.tripo3d.ai/blog/explore/texture-baking-from-ai-high-poly-to-low-poly). **Observed (vendor)**
- Blender Artists general cleanup practice: merge by distance, recalculate normals, tris-to-quads scripts (with warnings that auto tri→quad can misfire) — [Blender Artists mesh cleaning script](https://blenderartists.org/t/mesh-cleaning-script/695070); [Blender Artists add-ons for cleanup](https://blenderartists.org/t/addons-for-mesh-cleanup/682560). **Observed**

### Inferences
- For a modular avatar, separation should be *designed*, not *discovered*: define the part list (head, faceplate, torso shell, pelvis, 2× upper arm, 2× forearm, 2× hand, 2× thigh, 2× shin, 2× foot, T-shirt, sneaker) before generation and use segmentation only to cut a whole reconstruction along those seams; where seams fall inside a fused surface (shell over internals), a boolean/re-sculpt in Blender is unavoidable. **Inferred**
- Hidden/occluded interfaces (socket faces under a shell, the stump where a swappable arm meets the shoulder) will not be plausible from any completion model — they must be authored to the shared attachment convention. **Inferred**

### Gaps
- Whether Tripo "Complete Mesh Parts" and X-Part produce watertight separate GLBs with clean interface caps was not confirmable.

## KQ7. Garment fit and attachment conventions for modular avatars (RPM, VRM/VRoid, Mixamo/Modular Avatar, tutorials)

### Takeaway
Shipping modular-avatar systems converge on: one shared armature with fixed bone names, garments skinned to that armature and exported with it, body geometry under garments **removed (or blendshape-shrunk)** rather than occluded, one material per mesh, hard triangle budgets per slot, ≤4 weights/vertex normalised, and a deliberate overlap/cover at seams (RPM neck). Mixed-material limbs are not addressed by any of them; the closest analogue is RPM's per-slot mesh replacement on a fixed skeleton.

### Cited Findings
- Ready Player Me outfits: remove body parts hidden by clothing; outfit must exclude head/hair; cover the neck seam with clothing/accessories "to avoid unwanted clipping"; retain the template UV layout and **keep the armature**; triangle caps — outfit total 20,000; Wolf3D_Outfit_Top 6,000, Wolf3D_Outfit_Bottom 5,000, Wolf3D_Outfit_Footwear 2,000, Wolf3D_Body 2,000; one material per mesh; max 4 skin weights per vertex, normalised to 1.0; a Blender validation plugin gates upload — [RPM Fullbody Outfits (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-outfits); [RPM Modeling Guidelines (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-assets/modeling-guidelines). **Documented (excerpt)**

Official humanoid.md fetch failed (503). **Documented (secondary)**
- Outfits made for other rigs (Mixamo/VRoid) "have different bone names, so Modular Avatar can't auto-fit them" — [Booth listing (excerpt)](https://booth.pm/en/items/8514446). **Observed (promotional)**

- Body masks: Blender Studio stylized-character course comments describe extracting a mask from the body with mask tools; the DAZ importer wiki notes masks remain useful "to hide the skin beneath" even when clothes are in separate collections — [Blender Studio Stylized Character Workflow](https://studio.blender.org/training/stylized-character-workflow/5d7f7fc5db37a94301d88ff9); [Diffeomorphic Visibility wiki](https://bitbucket.org/Diffeomorphic/import_daz/wiki/Setup/Visibility). ### Inferences
- Convention set for this project, consistent with RPM/VRM/Modular Avatar: one armature with VRM/Mixamo-style humanoid names; every part (shell, silicone sleeve, robotic arm, T-shirt, sneaker) skinned to that armature and exported with it; attachment points expressed as bones or empties parented to bones (wrist/ankle/neck sockets); for each garment, author a vertex-group/shape-key "hide under garment" mask on the body/shell and **delete** covered faces for the mobile build (RPM/Modular Avatar both prefer deletion); keep a 1–2 mm (scaled) shrinkwrap offset for garment clearance and bake it as a shape key so variant bodies can re-conform. **Inferred**

- The T-shirt and sneaker should be modelled once over the *largest* variant (frosted shell) and the silicone/robotic bodies must fit inside that clearance envelope, else per-variant garment shape keys are needed. **Inferred**

## KQ8. Retopology, UV and baking decisions for a mobile browser avatar

### Takeaway
Practitioners and vendors agree AI topology is acceptable for static props but not for deforming characters; the choices are smart retopo in the generator (Tripo quad ≤10k quads, Meshy Remesh), Quad Remesher in Blender (most-praised for organic characters), or hand retopo for faces/hands/joints; then bake the AI texture onto the clean UVs with a cage. Mobile budgets in shipping avatar systems are ~20k tris total (RPM) with 1–2 materials and ≤4 weights/vertex; a single atlas, not UDIMs, is the norm.

### Cited Findings
- RPM budgets (see KQ7): 20,000-tri outfit cap, per-slot caps, one material per mesh — [RPM outfits (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-outfits). **Documented (excerpt)**
- Khronos 3D Commerce Real-time Asset Creation Guidelines v1.0 (2020, as quoted on the three.js forum): ≤100,000 triangles, ideally <5 MB, power-of-two textures (square not required), minimise draw calls; a 100 KB "preview" variant drops the normal map and uses low-res base colour; v2.0 announced at SIGGRAPH 2025 as a living document (numbers not retrieved) — [three.js discourse quoting the guidelines](https://discourse.threejs.org/t/maximum-3d-model-size-to-load/46077/7); [Khronos ACG 2.0 blog](https://www.khronos.org/blog/introducing-asset-creation-guidelines-2.0-siggraph-2025); [guidelines repo](https://github.com/mlimper/3DC-Asset-Creation/blob/main/asset-creation-guidelines/RealtimeAssetCreationGuidelines.md). **Documented (secondhand numbers)**
- Freelancer rule of thumb: mobile character 1,500–5,000 tris, PC/console 10,000–30,000 — [Fiverr listing (excerpt)](https://fiverr.com/anthony_qwe/retopology-your-3d-model-uv-unwrap-and-make-it-game-ready). **Unverified (service page)**
- Quad Remesher (Exoside; same developer as ZRemesher) converts to all-quad meshes at a target count; one guide calls it "the de facto choice for character retopology in Blender" (promotional) — [80.lv Quad Remesher announcement](https://80.lv/articles/quad-remesher-new-automatic-retopology-plugin); [SuperRendersFarm guide](https://superrendersfarm.com/article/quad-remesher-blender-retopology). **Documented / Unverified**
- Instant Meshes is free but "lower quality"; a Blender Artists user says cleaning holes often outweighs the gains; Blender Voxel Remesh gives blocky topology unsuitable for organic characters; QuadriFlow "refuses many of these meshes outright" on AI/scanned input per a vendor; a QRemeshify add-on matched Quad Remesher on some clothing meshes — [Blender Artists Tesselator thread](https://blenderartists.org/t/tesselator-quad-remesher/1131624?page=14); [Quadmend listing](https://superhivemarket.com/products/quadmend). **Observed / Unverified**
- Tripo smart retopo: quad max 10,000 quads (FBX) vs 20,000 tris per ComfyUI node docs; Scenario says 1k–20k target — see KQ1 — conflicting. **Documented (excerpt)**
- Manual bake route for AI textures (CSM Academy): import AI mesh as high-poly, duplicate and retopo, UV unwrap, duplicate low-poly as "Cage", Alt+S inflate to cover the high-poly, bake Selected-to-Active with cage — [CSM Academy: Retopology and Baking Textures](https://www.csm.ai/academy/retopology-and-baking-textures). Tripo: poor cage distance causes smearing/pinching; apply uniform subdivision to the high-poly before baking — [Tripo baking guide (excerpt)](https://www.tripo3d.ai/blog/explore/texture-baking-from-ai-high-poly-to-low-poly). **Observed**
- Automated transfer options: 3D AI Studio "Bake Texture" API aligns a textured GLB to a retopo mesh, generates UVs and bakes by ray casting (5 credits); Scenario's Tripo Retopology has a "Bake Textures" toggle — [3D AI Studio Bake Texture](https://www.3daistudio.com/Platform/API/Documentation/tools/bake-texture); [Scenario Tripo retopology](https://www.scenario.com/models/tripo-retopology). **Documented (excerpt)**
- Meshy: run Unwrap UV before texturing when seams/distortion appear; PBR sets at 2K/4K — [Meshy docs (excerpt)](https://docs.meshy.ai/ru/webapp/guides/3d-model/ai-texturing). **Documented (excerpt)**
- Hunyuan3D 2.1 ComfyUI wrapper offers a patched xatlas for UV unwrapping high-poly meshes — [visualbruno/ComfyUI-Hunyuan3d-2-1](https://github.com/visualbruno/ComfyUI-Hunyuan3d-2-1). **Documented**
- Khronos 3D Commerce validator checks file size, triangle count, material count, texture resolution, power-of-two, texel density and UV space — [3dc-validator README](https://cdn.jsdelivr.net/npm/@mikefesta/3dc-validator@1.0.0/README.md). **Documented**

### Inferences
- Keep AI topology only for rigid, non-deforming shells that will be decimated/remeshed anyway (e.g., sneaker sole, faceplate); for anything skinned across a joint (torso shell, silicone arm, T-shirt), retopologise (Quad Remesher or hand loops at shoulder/elbow/wrist). This matches the polycount/RPM/Tripo consensus that deformation is where AI topology fails. **Inferred**
- Budget target consistent with RPM-class phone avatars: ~15–25k tris for the whole assembled avatar, 1–2 atlases (2K body/shell, 1K–2K garments), one material per swappable part, no UDIMs (UDIMs are a DCC/VFX convention; every mobile avatar spec found uses single textures per mesh). **Inferred**
- Texel density: set from the garment/face close-up distance in the creator UI, not from the whole figure; the Khronos validator can enforce the chosen density. **Inferred**
- Bake AI albedo (and nothing else from the AI) onto clean UVs; author roughness/metallic/emissive by hand for the three material variants so variants are texture-driven. **Inferred**

### Gaps
- ACG 2.0 numeric budgets not retrieved.
- No measured comparison of Quad Remesher vs Tripo smart quad on the same character.

## KQ9. Rigging and deformation testing (Rigify / Auto-Rig Pro / Mixamo / AccuRIG / generator auto-rigs), weight checks for interchangeable arms

### Takeaway
Generator auto-rigs (Tripo Rigging v1.0 for bipeds, Meshy Animate) and free auto-riggers (AccuRIG 2, Mixamo) will produce a skeleton in under a minute but all expect an A/T-pose humanoid and are reported weak on stylized/hero characters; the Blender add-on route (Auto-Rig Pro, or Rigify + game-rig export) gives the control a 30-year designer wants, especially for identical seam weights across swappable arms.

### Cited Findings
- Tripo Rigging: "one-click auto skeleton for humanoid or creature characters, with skin weights", ~30 s; Tripo Animation preset library — [Tripo developer models page (excerpt)](https://developers.tripo3d.com/en/models). Scenario: Rigging v2.5 is for non-bipeds; "for biped models and humanoids, please continue using Tripo Rigging v1.0" — [Scenario Tripo Rigging v2.5 (excerpt)](https://www.scenario.com/models/tripo-rigging-v25). Tripo's own blog: AI skin weights "may need refinement for hero characters"; preset library smaller than Mixamo's — [Tripo easiest auto-rigging (excerpt)](https://www.tripo3d.ai/blog/easiest-auto-rigging-tool). **Documented (excerpt)**
- Meshy Animate: auto-rigs humanoid and quadruped characters, 500+ presets, exports rigged FBX/GLB; recommends starting from T- or A-pose; cannot handle a non-standard body plan; custom animation means exporting to Blender/Maya — [Meshy Animate guide (excerpt)](https://docs.meshy.ai/en/webapp/guides/animate). Bone hierarchy not documented. **Documented (excerpt)**
- AccuRIG 2 (Reallusion, free): 19-joint body rig plus finger rig; export presets for Blender/Unity/Unreal etc.; needs a free ActorCore account to export; a May 2026 test called it best free option for traditional humanoids but less suited to stylized/non-humanoid work and expects A-pose meshes facing a specific direction; mixed community reports (crashes; FBX "useless in Blender" for one pipeline) — [CG Channel AccuRIG 2.0 (excerpt)](https://www.cgchannel.com/?p=168596); [Stray Spark auto-rigging showdown 2026 (excerpt)](https://www.strayspark.studio/blog/ai-auto-rigging-showdown-2026-tripo-meshy-cascadeur-mixamo); [Reallusion forum (excerpt)](https://forum.reallusion.com/PrintTopic522024.aspx). **Observed**
- Mixamo: bipedal only, maintenance mode, 2025–26 outage, Blender add-on broke at 4.0 — [Cinevva (excerpt)](https://app.cinevva.com/guides/mixamo-to-blender-2026). **Observed**
- Auto-Rig Pro: FBX/glTF export, Unity/Unreal/Godot presets, Humanoid export type with retargeting and root motion, Mannequin naming, remapper works with "Auto-Rig Pro, Rigify, custom rigs" — [Blender Market ARP](https://blendermarket.com/products/auto-rig-pro/). **Documented (excerpt)**
- RPM constraints that any rig must satisfy: ≤4 weights/vertex, normalised — [RPM (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-outfits). **Documented (excerpt)**
- Hunyuan3D-Omni pose control can generate the mesh already in a specified skeletal pose (useful for forcing an A-pose) — [Hunyuan3D-Omni](https://github.com/Tencent-Hunyuan/Hunyuan3D-Omni). **Documented**

### Inferences
- Rig once on the master body with ARP or Rigify (deform bones only exported, humanoid names), then **transfer weights** to every variant part from the master body (Blender Data Transfer / vertex-group projection) so robotic and silicone arms inherit identical seam weights; auto-rigging each variant separately would break interchangeability. **Inferred**
- Deformation test set: elbow/knee 90–120° bends, shoulder raise, wrist twist, A↔T pose, plus a garment-clearance pose set; check silhouette match between variants in the same pose with a wireframe/X-ray overlay (blender-mcp's `look` tool can automate capture) — [blender-mcp README](https://github.com/ahujasid/blender-mcp). **Inferred**
- Generator auto-rigs are useful only to get a quick posed preview or Mixamo-compatible test animations; their skeletons should not become the project's shared armature. **Inferred**

### Gaps
- No documentation of Tripo/Meshy skeleton bone names or whether they match VRM/Mixamo naming.
- No evidence on auto-rig behaviour with detached/mixed-material limbs.

## KQ10. Which steps are repeatable automation vs visual judgment

### Takeaway
Everything downstream of a frozen master body and part list is scriptable (ComfyUI graphs for turnaround + reconstruction, Blender Python for cleanup/retopo/bake/export, batch validation); the irreducible judgment points are choosing the reconstruction, cutting seams, retopo flow at joints, material look of the frosted shell, and deformation review.

### Cited Findings
- blender-mcp exposes arbitrary Blender Python plus visual self-inspection (viewport/wireframe/X-ray/render) and asset/generator calls; its own docs warn complex requests must be split and time out — [ahujasid/blender-mcp README](https://github.com/ahujasid/blender-mcp). **Documented**
- ComfyUI has native/partner nodes for Hunyuan3D-2 and 2mv, Tripo (image→multiview, multiview→model, segment, retopology, texture, convert), Meshy multi-image, MV-Adapter, and TRELLIS.2 wrappers — [ComfyUI Hunyuan3D-2 tutorial (excerpt)](https://docs.comfy.org/tutorials/3d/hunyuan3d-2); [ComfyUI Tripo nodes (excerpt)](https://docs.comfy.org/built-in-nodes/TripoSmartSegmentNode); [comfy.org Meshy multi-image workflow](https://comfy.org/workflows/api_meshy_multi_image_to_model-5f8cb3a5e8f9/); [MV-Adapter](https://github.com/huanngzh/MV-Adapter); [ComfyUI-Trellis2](https://github.com/visualbruno/ComfyUI-Trellis2). **Documented**
- Scripted cleanup is already common practice (merge by distance, normals, tri→quad; polycount replier used Blender scripting for AI meshes) — [Blender Artists](https://blenderartists.org/t/mesh-cleaning-script/695070); [polycount](https://polycount.com/discussion/238705/how-are-you-actually-handling-ai-generated-mesh-cleanup-before-engine-handoff). **Observed**
- Batch validation of budgets/texel density/UVs exists (Khronos 3DC validator; RPM Blender validator) — [3dc-validator](https://cdn.jsdelivr.net/npm/@mikefesta/3dc-validator@1.0.0/README.md); [RPM (excerpt)](https://docs.readyplayer.me/ready-player-me/customizing-guides/create-custom-outfits). **Documented**
- Reviewers of LLM-in-Blender say it is "best for technical execution rather than creative direction" — [MindStudio (excerpt)](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance). **Observed**

### Inferences
- Automatable: material-neutral reference rendering; turnaround generation; batch reconstruction of candidates; mesh audit/repair; decimate/remesh to budget; cage bake of AI albedo; weight transfer from master body; export of every variant/garment combination; budget/validator checks; test-pose render contact sheets. **Inferred**
- Judgment-only: picking the candidate that matches the concept; placing part seams and attachment rings; retopo edge flow at the faceplate rim, shoulders, elbows, knees; frosted-shell look-dev and the baked internals; sign-off on deformation/clearance across variant combinations. **Inferred**

### Gaps
- No published end-to-end automation pipeline for modular AI-assisted characters was found; all sources describe single-asset workflows.
