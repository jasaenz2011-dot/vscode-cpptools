## Q2. Licensing and openness: what is open vs. closed hosted backend

### Takeaway
The desktop client is genuinely open (GPL-3.0-or-later for Mixar code, GPL-2.0-or-later for Blender-derived files, separate non-GPL brand license), but **the agent's brains are not in it**: the LLM orchestrator (LangGraph, "Claude Sonnet 4.6 primary, Gemini 3.1 Pro fallback", "18 tool domains / 200+ tools"), the tool prompts, the generation adapters, the material catalog and even the MCP tool list come from the closed `mixar-backend` at `api.mixar.app`. All AI features require a Mixar account; external PRs are not accepted pending a CLA.

## Q3. Authentication/providers: ChatGPT/Codex subscription, Claude subscription, API keys, local models

### Takeaway
The client's BYOK dialog offers four provider families: (1) backend-catalog cloud providers by API key (README names OpenAI and Anthropic; the list itself is server-defined), (2) OpenRouter key + any model slug, (3) **"Codex (ChatGPT sub)" — implemented by pasting your `~/.codex/auth.json` bundle (after `codex login`) into Mixar, which then sends that credential bundle to Mixar's backend**, and (4) "Local (this computer)" — a Mixar-managed llama.cpp runtime with curated Qwen/GPT-OSS GGUFs, or any OpenAI-compatible server (Ollama, LM Studio, llama.cpp, oMLX). **No Claude/Anthropic subscription sign-in exists** in the client. In every mode — including local — the orchestrator still runs on Mixar's backend and a Mixar account/sign-in is required.

### Inferences
- "Use your existing ChatGPT/Codex subscription" is real but the mechanism is **credential-bundle hand-off, not an in-app OAuth button**: the user copies OAuth tokens produced by OpenAI's Codex CLI into Mixar, and the client code says that bundle is sent as the credential to Mixar's backend, which then calls OpenAI's Codex endpoints on the user's behalf. Users should weigh (a) handing refresh tokens to a third-party server and (b) whether OpenAI's terms permit using ChatGPT-plan Codex access from a non-OpenAI application. ## Q5. Which operations run locally vs. send scene data/screenshots/files to a remote service

### Takeaway
Everything that touches `bpy` runs locally inside Blender's main thread, but the *decision loop* is remote: each turn uploads the message plus any attached images as base64 `data:` URLs; backend tools execute scripts locally and their results (JSON scene summaries, object diffs, and **base64 viewport/inspection renders**) go back to the backend "for the model"; "Folder as Context" streams file contents and image previews to the agent; generation/retopo/UV/rig jobs upload meshes (GLB) to Mixar's backend. ## Q7. Multi-agent support: real? How parallel agents share one Blender scene

### Takeaway
"Multi-agent" is implemented, with real engineering around Blender's main-thread constraint: **one Blender process executes all agent scripts serially on the main thread** (WebSocket thread enqueues → `bpy.app.timers` executes one script per tick, round-robin across per-scene-tab "lanes"), so parallelism inside the GUI process is interleaving, not concurrency. True parallel compute happens in **separate headless `Mixar --background` worker processes** spawned by a sandbox supervisor, whose results are merged back via a "fenced, journaled artifact commit" protocol, and in throwaway `agentlane:` scenes. Safety mechanisms (per-scene routing hard-fail, render gate, undo guard, viewport lock) were added after observed crashes.

### Cited Findings
- Executor contract: "scripts arrive on the WS receive thread; `bpy` runs on the main thread. The executor bridges them via a queue + a `bpy.app.timers.register`-driven timer"; "a main-thread timer executes ONE script per tick; long scripts must bound their own work because synchronous bpy still blocks the UI" — [ARCHITECTURE.md](https://github.com/Mixar-AI/mixar-app/blob/605ebe3406208c3a7a03c661033f756abd49427b/src/scripts/mixar/modules/space_mixie_chat/ARCHITECTURE.md), [main_thread_executor.py](https://github.com/Mixar-AI/mixar-app/blob/605ebe3406208c3a7a03c661033f756abd49427b/src/scripts/mixar/modules/space_mixie_chat/core/main_thread_executor.py). **Documented**

## Q10. Programmatic control: CLI, MCP server, HTTP/WebSocket API, Python API; comparison with vanilla Blender + blender-mcp / --background

### Takeaway
Since v4.2.2 (2026-10-04) Mixar ships an **opt-in MCP bridge**: a stdlib-only stdio launcher (`src/scripts/mixar/mcp.py`) that discovers a running, signed-in Mixar via local JSON records and relays to an authenticated loopback HTTP relay; tools include backend scene tools (scripting, materials/layers, UVs, generation, rendering, export), scene-tab tools (`mixar_scene_new/switch/scenes`), project tools, `mixar_tool_catalog`/`mixar_tool_quote`/`mixar_credit_balance`, and optional native UI-control tools (`mixar_ui_*`: observe controls, window images, clicks/keys). Compared with vanilla Blender + ahujasid/blender-mcp or `blender --background --python`, Mixar adds a sandboxed, scene-pinned, credit-metered tool surface but removes the ability to run fully offline.
